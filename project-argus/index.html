Introduction

QA across a portfolio of SaaS products means re-learning each product's rules, roles and quirks for every ticket. Argus is an AI QA agent, built on Claude Code with Playwright browser automation and Jira and GitHub integrations, that carries that knowledge from one ticket to the next and applies the same rigorous method every time.

🎫

Tests real tickets

Reads the ticket, comments, linked docs and the code change, builds a test plan, and runs it in a real browser against a test environment.

🧪

Beyond the happy path

Permission matrices, exploratory edge cases, error monitoring and cross-product checks, all backed by screenshot evidence.

🎭

Leaves regression behind

Turns passing tickets into Playwright tests using the Page Object Model, and opens a pull request to the product's test repo.

🧠

Learns every product

Feature quirks, regression patterns and coverage flow back into a per-product knowledge base after every ticket.

⚙️How it works

A small set of commands covers the whole QA lifecycle. The core loop runs once per ticket, and every pass feeds the knowledge base.

Onboard product→ Groom ticket→ Run ticket→ Update knowledge↺ Verify bug
CommandWhat it doesOutput
Groom ticketAnalyses the ticket and code before testing: acceptance criteria, testability, permissions, edge cases and risk.Test cases, plus questions for the developer
Run ticketThe full QA workflow: plan, execute, explore, report, automate and learn.Jira report, Playwright PR, knowledge PR
Verify bugThree reproduction attempts with variations, then a blast-radius check across roles and related screens.Reproduced, cannot reproduce or partial, with evidence
Update knowledgeRecords what a session learned: features, baselines, regression patterns and coverage.Updated product knowledge
Onboard productA guided session that discovers a product's stack, roles, environments and workflows.A ready-to-test product knowledge base
Onboard yourselfSets up a new team member's credentials and checks every integration.A verified, working setup

Inside a ticket run: 11 steps

  1. Load contextProduct config, knowledge base and environments.
  2. Read the ticketComments, linked issues, docs and the code diff.
  3. Pick the environmentResolves where to test for this ticket.
  4. Build the test planPositive and negative cases, permissions, and cases derived from the diff.
  5. ExecuteStructured tests with screenshot evidence.
  6. Explore & monitorEdge cases, error tracking and cross-product checks.
  7. Human reviewThe full report is shown to a person for approval.
  8. Post to JiraEvidence, comment, label and status.
  9. Clean upBrowser, screenshots and seeded data.
  10. AutomateGenerates or updates Playwright specs, and opens a PR.
  11. LearnUpdates the knowledge base, and opens a PR.

🧪Testing layers

Every run goes through the same layers, so even a small ticket gets more than a happy-path click-through.

LayerWhat it checks
StructuredEach acceptance criterion with screenshot evidence; a baseline check that unchanged behaviour still holds; positive and negative paths; every permission against every relevant role; and what happens after a change (messages, audit trails, lists, the back button). The browser console is checked after every action.
ExploratoryBoundaries and odd inputs, data scoping by role, double-submits, invalid API payloads, related features, known regression patterns near the change, and records in unexpected states.
MonitoringNew exceptions, performance regressions and error-log patterns that appear during the test window.
Cross-productWhere a feature integrates with another product, checks the other side of the integration too.
Bug reproductionThree attempts with variations, a blast-radius check across roles and screens, and a clear scope of who is affected.
AutomationPlaywright specs using the Page Object Model, with a coverage-gap analysis and data seeding, delivered as a pull request.

🪜Autonomy roadmap

Argus earns the removal of human approval steps one product at a time, on evidence, and can lose it again. Each product's level lives in its configuration, so every promotion or demotion is a reviewed pull request.

LevelWhat changesEntry criteria (per product)
L0Today: a person approves every report.Default
L1Clean passes post automatically. Failures, escalations, payments and authentication always go to a person.20+ runs in 90 days; zero confirmed false positives in 60 days; hard-intervention rate under 10%; full evidence coverage; no stale follow-ups
L2Auto-planning on documented features, and automatic status transitions. Knowledge PRs are still reviewed by a person.30 consecutive L1 runs with no overridden reports; zero false positives in 90 days; interventions under 5%
L3Unattended scheduled runs.Two quarters at L2; interventions under 5% across 50+ runs; organisation sign-off
⬇️

Automatic demotion

Any confirmed false positive drops the product one level immediately. Any integrity incident sends it straight back to L0.

🔒

Never removed

Human review of every generated PR, no testing in production, and a person for anything touching payments, authentication or data integrity.

📈

Measured weekly

A periodic audit produces the metrics every level is judged on, so the evidence is always current.
